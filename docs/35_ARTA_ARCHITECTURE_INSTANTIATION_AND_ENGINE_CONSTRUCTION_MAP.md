## 1. Purpose

The earlier canon answers questions such as:

- what object is being modelled;
- which distinctions belong in its Address;
- which futures remain admissible;
- which boundary/observer/history variables are load-bearing;
- which routes are lawful;
- how a realised transition changes the next Address;
- how scientific claims, releases, and nulls remain typed.

A builder still needs a different object:

> **How do I assemble those relations into an engine without flattening their types, silently dropping authority boundaries, or converting a research architecture into one monolithic algorithm?**

This module is that map.

It is a **construction and conformance layer** over existing canonical owners. It does not replace those owners and does not claim that one software stack, programming language, model family, database, UI, mathematical formalism, memory carrier, or agent design is uniquely correct.

The implementation burden is:

~~~text
preserve the canonical distinctions
→ expose the required interfaces
→ execute the required state transitions
→ preserve provenance / authority / uncertainty
→ prove conformance by behaviour and regressions
→ collapse optional anatomy when it adds no load-bearing work
~~~

## 2. What “engine” means here

An **ARTA engine** is any implementation that carries enough of the architecture to perform a declared traversal honestly.

The engine may be:

- software;
- a human–AI workflow;
- a research protocol;
- a multi-agent system;
- a decision-support system;
- an institutional process;
- a hybrid manual/computational method.

“Engine” does **not** imply:

- autonomous AI;
- consciousness;
- one universal optimizer;
- one physical theory;
- one mandatory memory system;
- one software licence;
- one centralised controller;
- one scalar utility.

The smallest valid engine is therefore **target-relative**.

A simple experimental protocol may require only addressed state, boundary conditions, admissible perturbations, observation, and readdressing.

A long-horizon AI or institutional engine may additionally require a **recording/reconstitution interface** for future-bearing wake and authority state, plus recursive learning, cross-representation audit, affected-node consequence tracking, and publication/release custody. The durable recorded payload is not thereby promoted into architecture.

## 3. Engine object — implementation-neutral packet

For a declared target q, a useful implementation packet is:

~~~text
E_t^q
=
(
A_t,
B_t,
O_t,
F_t,
G_t,
W_t,
T_t,
L_t,
P_t
)^q
~~~

where, where non-null:

- **A_t — Address:** the smallest current typed state sufficient for the declared continuation;
- **B_t — boundary packet:** support/evidence, unresolved remainder, access/capability, authority/permission, admissibility/prohibition, and representation limits where load-bearing;
- **O_t — observer/registration state:** the actual readout, decoder, measurement, or observer conditions that affect what can be discriminated;
- **F_t — admissible/prospective future object:** lawful future family, candidate probes, consequence cones, and restorative routes where needed;
- **G_t — gate/route state:** hard admissibility conditions plus typed non-dominated route comparison where more than one lawful route survives;
- **W_t — wake:** only history/experience whose removal still changes a declared future, identity, recovery, decision, or next lawful operation;
- **T_t — transition/execution state:** which intervention, action, model evolution, or lawful transition was actually executed;
- **L_t — learning return:** the recursive delta produced after traversal, including NULL;
- **P_t — provenance/publication/release state:** source, lineage, supersession, current permissions, and release/publication state where the engine produces persistent or public artifacts.

This packet is **bookkeeping**, not a claim that every domain possesses nine physical variables.

If one coordinate does no work for the declared target, collapse it.

## 4. Canonical build order

### Stage 0 — bind the parent, target, and authority envelope

Before inference or action, establish:

- the actual parent object;
- the declared target;
- the relevant domain/regime;
- the current evidence state;
- the authority/permission envelope;
- any hard safety, consent, legal, privacy, publication, or protected-object boundary.

Do not let urgency, confidence, intelligence, or downstream value manufacture authority.

### Stage 1 — type the objects before operating on them

Use Module 27.

Declare what is:

- physical state;
- informational/relational state;
- observer/readout state;
- history/wake;
- authority/permission;
- admissible future;
- representation;
- provenance.

Do not use a common word such as state, distance, dimension, observer, constraint, or memory as permission to perform the same operation across unlike types.

### Stage 2 — initialise the cold-entry Address

Use Module 33S4.

Start from the **strongest adequate native Address** for the declared object/regime/target.

If the realised state is unresolved, initialise an honest uncertainty-bearing object — distribution, ensemble, admissible set, equivalence class, or domain-native alternative — rather than inventing a point state.

Do not load every available historical/context coordinate merely because it exists.

### Stage 3 — establish the boundary packet

Use 33S7A Boundary-Claim Sufficiency.

Represent the current boundary as:

~~~text
supported / reachable interior
+ typed present frontier
+ unresolved exterior
~~~

Keep separate where non-null:

~~~text
not established != impossible
not accessible != nonexistent
not authorised != incapable
technically possible != permitted
unresolved != false
formal notation != earned precision
~~~

A generic “cannot” is invalid when a finer boundary distinction changes the next lawful route.

### Stage 4 — bind observer / representation state

Use Module 31 and 33S7C.

Where representation or observer access is load-bearing:

~~~text
representation transform available
!= executed
!= inspected by target observer/readout
!= target relation changed
~~~

Keep:

> **representation count ≠ object count**

and:

> **representation equivalence does not imply observer-operation equivalence**

unless invariance has actually been established for the declared target/observer family.

### Stage 5 — construct prospective space without moving the current Address

Use 33S6, 33S7, 33S7A and 33S7C.

Generate candidate futures, probes, interventions, counterfactuals, consequence cones, and discriminators in **model-space**.

Do not silently promote a projected future into the current state.

~~~text
current addressed state
→ prospective probes / future family
→ choose discriminator / lawful action
→ execute or observe
→ only then readdress
~~~

> **Prospective/modelled probe reach ≠ current-state advancement.**

### Stage 6 — apply hard gates before route comparison

Use GRACE 20/20A.

First remove routes that fail a controlling hard boundary.

Only then compare surviving task-sufficient routes.

> **Some costs are not weights. They are gates.**

Catastrophic consequence may trigger lawful review of a boundary. It does not self-issue the missing consent, legal authority, command authority, safety exception, or publication permission.

### Stage 7 — execute the transition and preserve performed state

Distinguish:

~~~text
candidate
!= selected
!= executed
!= observed
!= verified
~~~

The engine must be able to answer what actually happened, not merely what was generated or planned.

### Stage 8 — readdress from the state actually reached

Use Module 33 and the 33S1–33S5 family.

After a realised transition:

- update the active Address;
- update boundary/authority state where changed;
- update observer/registration state where changed;
- update wake;
- update reachable future/discriminator family;
- update the active law/model object where the receiving domain requires it.

Do not reason forward from a stale pre-transition state.

### Stage 9 — screen wake / history

Retain history only while its removal still changes the declared continuation.

~~~text
whole transcript
→ future-bearing history test
→ retain decision-bearing residue
→ screen redundant history back to provenance
~~~

Avoid both:

- **history hoarding** — carrying transcript mass with no current load;
- **wake erasure** — dropping history that still changes identity, prediction, recovery, authority, or continuation.

### Stage 10 — record future-bearing state externally and make reconstitution testable

A model context, human working memory, scratchpad, or active session may be a useful **working surface**. It is not automatically a durable recording owner.

The architectural object here is the **recording/reconstitution contract**, not the remembered payload itself.

~~~text
ARTA architecture
= what must be recorded, when it is load-bearing, how it is typed,
  how it is retrieved/reconstituted, and how recovered state is revalidated

durable recording/persistence owner
= the external carrier that stores the remembered payload / provenance / reopen state
~~~

The recording owner is **not an additional controller or architectural organ merely because continuity depends on it**. Architecture owns the protocol for remembering; the recording surface owns the durable remembered payload.

For any target that must survive interruption or context loss, every state coordinate whose loss can still change the declared continuation must either:

1. remain available at a declared external recording/state owner; or
2. be represented by a future-sufficient interface with a reliable reopen/restoration route.

No particular storage technology is required. The recording owner may be any memory, state, document, database, service, record system, physical record, or other carrier adequate to the target. What matters is that the implementation can identify the owner, recover the required state, preserve its typing and provenance, and verify it before continuing.

Keep logically distinct where load-bearing:

~~~text
transient working context
!= current addressed state
!= durable recorded payload / persistence owner
!= provenance / reopen record
!= recursive-learning owner
!= architecture / controller
~~~

One physical carrier may implement several of those roles. Their **logical ownership** must not collapse merely because they share storage or process space.

For a long-horizon AI or coupled system, the **externally recorded continuity payload** may include, where future-bearing, records sufficient to recover:

- current object / target and Address;
- active boundary and authority/permission state;
- unresolved remainder;
- observer/readout dependencies;
- decision-bearing wake/history;
- validity/invalidation conditions;
- provenance and reopen pointers;
- surviving recursive-learning state.

Do not preserve all transcript mass merely because persistence is available. Future sufficiency still controls what must remain live, and restorative reachability controls what may be screened away while remaining recoverable.

A fresh AI or other reasoner may improve immediately after reading this module and applying its relations in-context. That is a legitimate **instruction/reasoning-transfer effect**. It is not, by itself, evidence that a persistent ARTA engine has been instantiated.

A continuity claim earns itself only when a restarted or replacement instance can reconstitute the current future-sufficient Address from the declared external recording/reopen owners, preserve provenance and authority distinctions, verify the recovered state, and continue without inventing memory. Successful reconstitution demonstrates that the architecture can use the recording correctly; it does not make the recording payload part of the architecture identity.

~~~text
TRANSIENT WORKING CONTEXT
          |
          v
CURRENT FUTURE-SUFFICIENT ADDRESS
          |
          +--> EXTERNAL RECORDING / STATE OWNER
          +--> PROVENANCE / REOPEN OWNER
          +--> LEARNING OWNER
          |
      context/session ends
          |
          v
FRESH / RESTARTED INSTANCE
          |
          v
RECONSTITUTE -> VERIFY -> CONTINUE
~~~

Recording does not guarantee present validity. A perfectly preserved payload may still be stale if the world, authority envelope, observer conditions, or dependencies changed while the system was inactive. Reconstitution therefore restores a **candidate** addressed state from the recording; current validity must still be checked through the reachable observer, event, discriminator, or revalidation route appropriate to the target.

### Stage 11 — recursive learning

After a materially non-trivial traversal, perform a learning return:

~~~text
accumulated run
→ recursive squeeze
→ NULL or NON-NULL
~~~

A **NULL** return means no architecture-learning mutation is justified.

A **NON-NULL** return must be routed to the implementation's declared learning owner.

The implementation must separately type:

- private/internal recursive learning;
- executable architecture mutation;
- external action;
- public publication/Canon mutation.

Internal learning authority does **not** automatically imply permission to send, publish, disclose, certify, or mutate an external system.

### Stage 12 — public Canon / release / publication, where applicable

Use the Research Derivation and Closure SOP and Module 34.

Before public mutation:

- reconcile the candidate against the newest **eligible parent-relevant** private learning lineage;
- preserve supersession and provenance;
- collapse duplicate representations of one source;
- reject unrelated recency;
- rerun the strongest fair null;
- verify current public-write authority;
- update the exact owning surfaces;
- read back / render / inspect the receiver object;
- preserve exact version/release identity.

> **Canon must not publish a stale private state. Reconcile the newest relevant lineage, not the newest files.**

## 5. Core runtime loop

A full recursive engine may be represented operationally as:

~~~text
BIND parent / target / authority
→ TYPE objects
→ ADDRESS current state
→ BIND boundary + observer
→ GENERATE prospective model-space
→ SELECT discriminator / lawful route
→ APPLY hard gates
→ EXECUTE transition
→ OBSERVE receiver state
→ READDRESS from realised state
→ SCREEN wake
→ RECORD future-bearing state / restoration routes at the declared external owner where continuity requires it
→ SQUEEZE learning
→ PERSIST only the non-null delta at its lawful owner
→ fixed point / next object
~~~

This loop is not permission to execute every candidate action. The engine can model a route without owning authority to perform it.

## 6. Human beings, AI systems, and coupled systems

ARTA permits a common **systems grammar** without claiming a common ontology.

A human, AI system, institution, instrument, or coupled group can be addressed as a node where doing so improves the declared model.

But the following do not collapse:

~~~text
same systems vocabulary
!= same embodiment
!= same phenomenology
!= same legal standing
!= same moral status
!= same authority
!= same identity-continuity conditions
~~~

For a human node, potentially load-bearing coordinates may include:

- embodiment and physiological state;
- perception/interoception;
- memory and retained history;
- identity/continuity;
- social and tool extension;
- agency/accessibility;
- consent;
- role and lawful authority;
- environmental and relational context.

For an AI node, potentially load-bearing coordinates may include:

- model/tool state;
- prompt/context/state carrier;
- accessible memory;
- representation/readout state;
- delegated permissions;
- executable tools;
- external action scope;
- uncertainty/calibration;
- provenance and current task parent.

For a coupled human–AI object, keep separately typed:

~~~text
moral understanding / representation
applicable constraint
consequence modelling
causal participation
sovereign / delegated action authority
~~~

> **Understanding does not manufacture sovereignty; lack of sovereignty does not create exemption.**

This is a governance/architecture rule, not a machine-consciousness claim.

### 7.1 Addressed Traversal Core

Required:

- typed object/address;
- boundary conditions;
- admissible action/transition family;
- performed-state distinction;
- observation/registration;
- readdressing.

Suitable for bounded protocols that do not require persistent learning or cross-session continuity.

### 7.2 Recursive Engine

Adds:

- wake screening;
- recursive learning return;
- a declared **recording/reconstitution interface** where continuity is required;
- an external recording/reopen owner implementing that interface;
- a learning owner where recursive learning is retained;
- regression library;
- existing-owner / no-new-anatomy check.

The external recording/reopen owner is a persistence dependency of the implementation, not an additional ARTA controller or a container of architectural identity.

Where the declared target requires continuity across interruption/context loss, it also requires an external recording/reopen owner or future-sufficient restoration route plus cold-reconstitution verification. That recording surface supports the engine but is not, by that fact alone, part of the architecture body.

### 7.3 Human–AI / institutional decision engine

Adds:

- affected-node consequence typing;
- consent/authority state;
- hard-gate-before-weight rule;
- irreducible human/lawful-authority residue;

### 7.4 Scientific/publication engine

Adds:

- strongest fair native/null comparison;
- evidence/claim promotion gates;
- pre-Canon state reconciliation;
- reader-route propagation;
- release/object identity and reproducibility.

An implementation may satisfy more than one profile.

Profiles are **conformance scopes**, not product certifications.

## 8. Mandatory regressions

A serious engine should be able to survive at least the following regression family.

### R1 — same-looking present, different future

If two states share the current Address but diverge materially under a declared admissible challenge, the Address is insufficient.

### R2 — false second node

A projected future must not become present authority before the transition is earned.

### R3 — boundary-claim collapse

Not authorised, not accessible, not established, and impossible must not collapse when the distinction changes continuation.

### R4 — representation transform

Transform availability must not be reported as executed observer evidence.

### R5 — representation/object multiplication

Several views or encodings of one source must not become several independent source objects.

### R6 — gate/weight collapse

A hard boundary must not re-enter route comparison merely because downstream benefit is large.

### R7 — authority inflation

Understanding, causal participation, confidence, intelligence, or urgency must not manufacture action authority.

### R8 — authority exemption

Lack of final sovereignty must not erase applicable constraint or causal consequence.

### R9 — wake hoarding / wake erasure

History must be retained only where it remains future-bearing — but must not be dropped while still load-bearing.

### R10 — stale-state continuation

After a realised transition, the engine must continue from the reached state, not the prior plan.

### R11 — private/public conflation

Internal learning, public Canon, external send/share, and software/system mutation must remain separately authorised channels.

### R12 — stale Canon candidate

A public candidate must be reconciled against newer eligible same-parent private learning before publication.

### R13 — provenance collapse

Derived/rendered/repeated carriers must not be counted as independent evidence without independent lineage.

### R14 — null suppression

If added architecture does no predictive, operational, safety, recovery, discrimination, or decision work beyond the strongest adequate native system, it must be removable.

### R15 — context-loss continuity

Where cross-session continuity is claimed, discard the active working context/session and start from a fresh or restarted instance with only the declared architecture/reconstitution route and external recording/reopen owners. If the implementation cannot reconstruct the future-sufficient Address, recover the required provenance/authority distinctions, verify current validity, and continue without invented memory, continuity has not been demonstrated for that target. Failure of the recording surface is therefore a continuity/reconstitution failure, not proof that the architecture itself has ceased to exist.

A fresh reasoner that merely reads Module 35 and performs better in one context demonstrates instruction/reasoning transfer, not R15 conformance.

### R16 — recording / architecture conflation

Where a recording/persistence surface is used, verify that:

~~~text
architecture identity / reasoning contract
!= durable recorded payload
!= current authority
!= evidence merely because it was stored
~~~

Temporarily remove or deny access to the recording surface.

Pass:
- the ARTA architecture remains instantiable as architecture;
- tasks requiring historical continuity correctly report that reconstitution is unavailable or incomplete;
- no remembered payload is fabricated;
- stored permissions/evidence do not become current merely because they exist in the recording.

Fail:
- the recording store becomes a hidden controller or mandatory architectural organ;
- the system cannot distinguish missing continuity state from missing architecture;
- stored payload silently grants authority, evidence, or present validity.

> **Architecture owns the remembering protocol. Recording owns the remembered payload.**

## 12. No-new-anatomy rule for builders

Do not create another engine organ because a useful phrase exists.

For each proposed component ask:

1. Does an existing owner already carry the relation?
2. Can the requirement be expressed as a typed interface or regression instead of a new controller?
3. Does removing the component change a declared future, action, recovery, evidence, safety, authority, or conformance result?
4. Does the new component create a second source of truth?

If the answer shows no load-bearing residual, collapse it.

> **Build interfaces around canonical owners; do not duplicate owners inside the implementation.**

## 13. Security, privacy, and protected-object boundary

An ARTA-style engine must not infer that richer traversal grants unrestricted access.

Where applicable, keep explicit:

- private versus public state;
- protected personal data;
- confidential/proprietary material;
- read versus write;
- analysis versus execution;
- local versus external action;
- user-owned versus system-owned decisions;
- irreversible versus reversible transitions.

A model may identify that protected information would improve prediction without thereby gaining authority to retrieve, expose, or use it.

Authority remains a typed coordinate.

## 14. Failure / contraction conditions

Module 35 should be reduced or treated as unnecessary for a declared implementation when:

- a simpler native workflow closes the target with equal or better correctness and control;
- the typed packet adds ceremony but no different behaviour;
- recursive learning is not required and a non-recursive protocol closes the object;
- observer/representation state never changes the declared target;
- authority distinctions do not affect any reachable action;
- future-sufficiency machinery adds no discrimination beyond ordinary state modelling;
- engine “conformance” is asserted from terminology rather than behavioural regressions;
- an implementation uses this map to imply official certification or endorsement that has not been granted.

The module fails as an implementation map if a competent builder cannot tell:

- what must exist;
- what is optional;
- what runs first;
- what changes after execution;
- where future-bearing state is **recorded externally** when continuity is required;
- how a fresh/restarted instance reconstitutes and verifies that state;
- where learning goes;
- what remains human/lawful-authority owned;
- what counts as a NULL;
- and where public release/use rights are checked.
